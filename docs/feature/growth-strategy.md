### 実装状況の確認で判明した3点

コードを確認した結果、当初の提案書（`vod-comong-soon-pipeline.md`）の前提を修正すべき点が3つ見つかった。

1. **`/{locale}/vod/{service}` アーカイブは既に実装済み**（`src/pages/vod/[slug]/index.tsx`）。提案書の「優先度S: サービス別ページとの連携」は**ゼロからの新規構築ではなく既存ページの強化**として扱える。最短距離の施策であり Phase 1 で最優先とする

## 1. 戦略の骨格 — 「ニュースで集め、レビューで留める」

### 問題の構造

ニュースメディア化には固有のジレンマがある。

```
ニュース記事を増やす
  → 流入は増える
  → しかし「浅いサイト」と評価されるとレビューの権威性が毀損する
  → E-E-A-T 低下 → 全体の順位下落
```

Katsumascore の競争優位は**レビューの質と独自スコア**であり、ニュース速報性では映画.com・シネマトゥデイ・Filmarks に勝てない。したがって戦略は「ニュースで勝つ」ではなく、

> **ニュース/配信情報は「入口」に徹し、滞在と評価はレビューが担う。**

という役割分担を徹底することにある。

### 3層モデル

```
┌─ 第1層：入口（Acquisition）────────────────────┐
│  配信カレンダー / 新着配信 / 劇場公開 / Xニュース    │
│  → 検索・Discover・SNSから「今」の需要を取る        │
│  KPI: セッション数、Discover表示回数、X経由流入       │
└──────────────────┬───────────────────────┘
                   │ 内部リンク（設計の要）
┌─ 第2層：回遊（Engagement）──────────────────┐
│  作品ページ / サービス別アーカイブ / ジャンル別まとめ  │
│  → 「何を観るか」の意思決定を支援                   │
│  KPI: セッションあたりPV、直帰率                    │
└──────────────────┬───────────────────────┘
                   │
┌─ 第3層：資産（Authority）───────────────────┐
│  レビュー / 考察 / person / company / series        │
│  → 独自スコアと文章。ここだけは代替不可              │
│  KPI: 滞在時間、指名検索、被リンク                  │
└──────────────────────────────────────────┘
```

**設計原則**：第1層のページは、それ単体で完結させず**必ず第2・第3層への導線を持つ**。逆に第3層のレビュー記事には**第1層の鮮度情報（今どこで観れるか）を埋め込む**。この双方向リンクが、ニュースの流入をレビューの評価に変換する機構になる。

## 2. 施策一覧

`vod-comong-soon-pipeline.md` の10案を戦略軸で再評価し、新規案を追加した。

### 2.1 VOD軸（既存提案の再評価）

#### A. サービス別ページの「配信カレンダー化」【優先度：S / 最優先】

既存の `/{locale}/vod/{service}` は現状「そのサービスで配信中の作品一覧」である。これを**時系列を持つカレンダーページ**に拡張する。

```
/ja/vod/netflix

┌────────────────────────────┐
│ Netflix 配信作品            │
├────────────────────────────┤
│ 【今週配信開始】             │  ← streaming_started_at が7日以内
│   作品カード（スコア付き）     │
├────────────────────────────┤
│ 【今月配信開始】             │  ← 30日以内
├────────────────────────────┤
│ 【配信予定】                 │  ← Coming Soon 連携（Phase 3）
├────────────────────────────┤
│ 【Netflix 高評価レビュー】    │  ← review_score 降順
├────────────────────────────┤
│ 【配信中の全作品】            │  ← 既存のアーカイブ部分
└────────────────────────────┘
```

**なぜ最優先か**：
- ページ自体が既に存在し、`streaming_started_at` のデータも既に蓄積されている。**新規データ取得が不要**
- 「netflix 新作 映画」「アマプラ 新着」は月間検索ボリュームが大きく、かつ**毎月更新され続けるクエリ**（＝一度上位を取れば資産になる）
- サービス名 × 新着は Google Discover の親和性が非常に高い

**必要な作業**：フロントの `/vod/[slug]` 拡張、WP REST API に `streaming_started_at` でのソート/絞り込みを追加。

---

#### B. 作品ページへの「今どこで観れるか」ブロック【優先度：S】

`vod-comong-soon-pipeline.md` 案6の逆リンク。これは**流入増より回遊・滞在の施策**である。

レビュー記事の読了地点に、

```
▼ 配信中サービス
Netflix / U-NEXT（見放題）
Amazon Prime Video（レンタル ¥400）
最終確認: 2026-08-01
```

を表示する。**「最終確認日」の明示が重要**で、これは Filmarks・JustWatch に対する信頼性の差別化になると同時に、E-E-A-T の「情報の鮮度管理」シグナルにもなる。

ACF に既にデータがあるため、**フロント実装のみで完結する**。

---

#### C. 編集部おすすめ（Editor's Pick）【優先度：S】

案1をそのまま採用。ただし戦略的位置付けを明確にする。

**これは「AIが自動生成したページ」と「メディアが編集したページ」を分ける唯一の要素である。** Google の Helpful Content 評価において、自動生成された一覧ページは低評価を受けやすい。冒頭に編集者の一次情報（なぜこの作品を推すか）が入ることで、ページ全体の性質が変わる。

実装は重くない：週次パッチの Slack 通知に「今週の新着」が既に届いているので、そこから1〜3作品を選び ACF に一言コメントを入れるだけの運用フローで足りる。

---

#### D. ジャンル×サービスの交差ページ【優先度：A】

案5の発展。単なる「ジャンル別まとめ」ではなく**交差ページ**にすることで、ロングテールの獲得数が桁違いになる。

```
/ja/vod/netflix/genre/sf     → 「Netflix SF映画 おすすめ」
/ja/vod/unext/genre/anime    → 「U-NEXT アニメ 見放題」
```

既存の genre taxonomy と vod taxonomy の AND 条件で自動生成できる。9サービス × 主要ジャンル10 = 約90ページ。

**注意**：全組み合わせを機械的に生成すると薄いページが大量発生し逆効果になる。**作品数が一定数（例: 10件）以上ある組み合わせのみ生成**し、それ以下は noindex またはページ自体を作らない、という閾値制御を必ず入れる。

---

#### E. 年間/月間アーカイブ【優先度：B に引き下げ】

案4は優先度Aとされていたが、**Bに引き下げることを提案する**。

理由：「2026年 Netflix追加作品」は検索需要が「今週/今月」に比べて明確に小さい。過去の配信情報を探すユーザーは少数で、多くは「今観れるもの」を探している。A（カレンダー化）が先に効いてから、その副産物として自動生成すれば足りる。

---

#### F. CPT名称の見直し【優先度：B・ただし判断は今】

案7。`vod_news` → `vod_calendar` などへの改称。

**優先度はBだが、意思決定は Phase 1 の前に済ませるべき**。CPT名はURL構造に影響し、後から変えるとリダイレクト対応が必要になる。まだ本格運用前の今なら無コストで変えられる。

推奨は `vod_release`（配信リリース情報の意。カレンダー表示は用途の一つに過ぎないため `calendar` より汎用的）。

### 2.2 新規案 — 検索需要を直接取りに行く

#### G. 「どこで見れる？」検索クエリの獲得【優先度：S / 新規・最重要】

**これが本戦略で最も見落とされている大きな機会である。**

映画・アニメの検索需要で最大級のクエリ群は「**{作品名} どこで見れる**」「**{作品名} 配信**」「**{作品名} netflix**」である。このクエリの現在の勝者は JustWatch・Filmarks・個人アフィリエイトブログだが、

- JustWatch は日本語コンテンツが機械翻訳的で薄い
- アフィリエイトブログは情報が古く、レビューがない

Katsumascore は**正確な配信情報（スクレイパーで自動更新）＋独自レビュー＋スコア**という、この3つを同時に持つ唯一のポジションにいる。

**実装**：作品ページのタイトル・見出し・構造化データを「どこで見れる」クエリに最適化する。

```
<title>『作品名』の配信はどこで見れる？Netflix・U-NEXT配信状況とレビュー | Katsumascore</title>

H1: 作品名
H2: 『作品名』はどこで配信中？（← 配信状況テーブル）
H2: レビュー・評価（← 既存の本文）
```

新規ページを作る必要がなく、**既存の全レビュー記事のタイトル・構造を調整するだけ**で効く。VOD配信情報を持っているからこそ書ける見出しであり、まさに「VOD情報がレビューへの入口になる」という本戦略の核心そのもの。

---

#### H. 構造化データ（JSON-LD）の是正【優先度：S / 新規】

実装状況を確認したところ、[`SeoHead.tsx`](../../../katsumascore-front/src/components/features/seo/SeoHead/SeoHead.tsx) で `Product` + `Review` + `aggregateRating` + `BreadcrumbList` が**既に出力されている**。person / franchise / company の各CPTにも個別のJSON-LDがある。

したがって本項は「新規実装」ではなく**是正**である。現状には検索結果に影響しうる問題が2点ある。

**問題1：作品ページの `@type` が `Product`**

映画・アニメ作品に対して `Product` を使っている（`SeoHead.tsx:54`）。Google は映画作品に対して `Movie` / `TVSeries` を想定しており、`Product` はレビューリッチリザルトの対象タイプではあるものの、映画向けの拡張（監督・出演者・公開年などのSERP表示）が一切効かない。

```
Product  →  Movie / TVSeries（post.type で分岐）
```

に変更し、`director` / `actor` / `datePublished` / `genre` を付与すると、既存の person・genre データがそのままSERPの情報量に変わる。

**問題2：`aggregateRating` の `reviewCount: 1`**

`SeoHead.tsx:76` で `reviewCount` を固定値 1 にしている。`aggregateRating` は本来「複数の評価の集約」を表すもので、評価が1件なら `Review` 単体で表現するのが正しい。Google のレビュースニペットのガイドライン上、この形は無効と判定される（＝★が表示されない）可能性がある。

**推奨**：`aggregateRating` を外し、`Review` + `reviewRating`（編集部による単一レビュー）に一本化する。`author` は既に指定済みだが、サイト名ではなく実際の評価者（`Organization` または実名の `Person`）にするとE-E-A-T上も整合する。

**追加すべきもの**

| スキーマ | 対象ページ | 状態 |
|---|---|---|
| `Movie` / `TVSeries` | 作品ページ | **要変更**（現状 `Product`） |
| `Review` + `reviewRating` | 作品ページ | 実装済み（`author` の見直し推奨） |
| `aggregateRating` | 作品ページ | **要削除または是正**（`reviewCount: 1`） |
| `BreadcrumbList` | 作品ページ | 実装済み |
| `WatchAction` / `offers` | 配信情報ブロック | 未実装。B とセットで追加 |
| `ItemList` | 一覧・カレンダーページ | 未実装。A とセットで追加 |

> `aggregateRating` は自作自演レビューとみなされるとペナルティ対象になる。単一の編集部評価を `aggregateRating` として出す現状の形は、この観点でもリスクがある。

#### I. Google Discover 最適化【優先度：S】

案9を具体化する。Discover は**日本の映画・アニメ系メディアにとって検索を超える流入源**になりうる。

Discover に載る条件：

| 要件 | 現状 | 対応 |
|---|---|---|
| 1200px以上の高品質画像 + `max-image-preview:large` | **未設定（確認済み）** | 下記の通り即対応 |
| 鮮度（数日以内の公開） | カレンダー記事が該当 | Phase 1 で自動的に満たす |
| 明確なトピック性 | 作品単位なら明確 | 一覧より個別作品記事が有利 |
| E-E-A-T（著者情報・運営者情報） | about ページあり | 著者ページ・プロフィール構造化 |
| クリックベイトでないタイトル | news_bot の見出しは事実ベース維持済み | 現状維持 |

**`max-image-preview:large` が未設定であることを確認した。** リポジトリ内で `robots` メタタグが出力されているのは [`SeoHead.tsx:27`](../../../katsumascore-front/src/components/features/seo/SeoHead/SeoHead.tsx) の `noindex` 分岐のみで、通常の記事ページには `robots` メタが一切出ていない。`_document.tsx` にも記述はない。

この状態では Google は画像プレビューをデフォルトサイズ（小）に制限するため、**Discover に載る条件をそもそも満たしていない**。Discover は大きなカード画像が前提のフォーマットであり、これは事実上のブロッカーになっている。

対応は `_document.tsx` の `<Head>`（全ページ共通）に1行入れるだけで済む。

```tsx
<meta name='robots' content='max-image-preview:large, max-snippet:-1, max-video-preview:-1' />
```

> `SeoHead` の `noindex` 分岐はページ個別に `robots` を上書きするため、共通側に置いても noindex 指定と競合しない点は確認が必要（Next.js の `Head` は後勝ちだが、`_document` と `next/head` はマージ経路が異なるため、実機で出力HTMLを確認すること）。

**本戦略で最も投資対効果が高い1行**であり、Phase 1 の先頭に置く理由もここにある。

### 2.3 SNS施策

#### J. news_bot の送客先を自サイトへ切り替える【優先度：S】

現在の news_bot は外部メディアのニュースをXに投稿しており、**リンク先は外部サイト**である。これは「Katsumascore のフォロワーを増やす」効果はあっても「Katsumascore への流入を増やす」効果はほぼない。

x-news-bot-spec.md 4.7 で既に正しく認識されている通り：

> リプライURLは…`wp_post_id`から解決したkatsumascore自身のレビュー記事URLを使用する。ニュースの転載ではなく自サイトへの送客を主目的とする

**この方針を、Coming Soon 連携（未実装）を待たずに前倒しで適用できる。**

現在稼働中の VOD スクレイパーは `streaming_started_at` で新規配信を検知し、既に Slack へ通知している。この新着配信こそが「自サイトのURLを持つニュース」であり、外部RSSより送客価値が高い。

```
週次パッチ → 新規配信検知 → Slack通知（実装済み）
                              ↓ 追加
                        X投稿案生成（自サイトURL付き）
```

**投稿フォーマット案**：

```
【配信開始】
『インターステラー』が Netflix で配信開始

Katsumascore スコア 4.5 / 5
「時間と重力を軸にした構成が…」

レビュー → https://katsumascore.blog/ja/movie/interstellar
```

外部ニュースの転載と違い、**自分の一次コンテンツを配る形になるため、投稿の独自性・エンゲージメントとも高くなる**。

---

#### K. プラットフォーム分散【優先度：A】

X 単独依存はリーチ上限・API費用の両面でリスクがある。既存の投稿文生成（`compose.py`）をそのまま流用できる先：

| プラットフォーム | コスト | 特性 |
|---|---|---|
| **Threads** | API無料 | 日本の映画・アニメ層が厚い。X文面をほぼそのまま流用可 |
| **Bluesky** | API無料 | アーリーアダプター層。競合が少なく相対的に目立つ |
| **Instagram（作品カード画像）** | API無料 | ビジュアル資産があれば強い。ポスター著作権に注意 |
| **YouTube Shorts** | — | 既にシート設計あり（spec 5.⑥）。工数は大きい |

**Threads と Bluesky は同一投稿文を流用でき、追加コストがほぼゼロ**。優先して着手する価値がある。

> 実装コストの実態: `compose.pack_thread()` の出力を各APIに投げるアダプタを追加するだけで、判定・生成ロジックは共通化できる。

#### L. 承認フローのワンクリック化【優先度：B】

案8。運用工数削減の施策であり流入には直結しないが、**施策数が増えるほど運用がボトルネックになる**ため、Phase 2 以降で必要になる。

## 3. 実行ロードマップ

投資対効果と依存関係で並べ替えた。**「既存データを使うだけで効く施策」を先に、「新規パイプラインが必要な施策」を後に**置いている。

### Phase 1 — 既存資産の刈り取り（新規データ取得ゼロ）

> 目的：今あるデータとページで取れる流入を全部取る。1〜2ヶ月。

## 4. 測定設計

施策を打つ前に計測を用意する。以下がないと Phase 1 の効果を検証できない。

| 指標 | 取得元 | 目的 |
|---|---|---|
| ページ種別ごとのセッション | GA4（カスタムディメンション） | 第1層/第2層/第3層の流入内訳 |
| 第1層 → 第3層の遷移率 | GA4 経路探索 | **本戦略の成否を測る最重要指標** |
| Discover 表示回数・CTR | Search Console | I の効果測定 |
| 「どこで見れる」系クエリの順位・表示回数 | Search Console | G の効果測定 |
| リッチリザルト表示 | Search Console（拡張レポート） | H の効果測定 |
| X/Threads 経由セッション | GA4（UTMパラメータ） | J・K の効果測定 |

**特に「第1層 → 第3層の遷移率」**。これが低いままセッションだけ増えているなら、ニュースが単なる浅いトラフィックを呼んでいるだけで、戦略が機能していないことを意味する。この場合は施策を増やすのではなく内部リンク設計を見直す。

## 5. リスクと歯止め

| リスク | 内容 | 歯止め |
|---|---|---|
| **薄いページの量産** | 交差ページ・アーカイブの自動生成で低品質ページが増え、サイト全体の評価が下がる | 作品数の閾値制御（例: 10件未満は生成しない / noindex）。D・E に必ず適用する |
| **レビューの希薄化** | ニュース記事の比率が上がり「レビューサイト」の認知が薄れる | 第3層の更新頻度を維持。TOP・サイト構造ではレビューを主役に置き続ける |
| **配信情報の誤り** | スクレイパーの誤判定で誤情報を掲載し信頼を失う | 「最終確認日」の明示。`ended` 判定は保守的に。エラー時は前回値を保持 |
| **X API コスト** | 自動投稿再開時に従量課金が膨らむ | 現在の手動投稿方式を維持。無料APIのThreads/Blueskyを先に拡張 |
| **AI生成コンテンツの評価** | 自動生成記事が Helpful Content 的に低評価を受ける | 編集部おすすめ【C】を必須要素とする。全自動記事を作らない |
| **著作権** | ポスター画像・あらすじの転載 | TMDb の利用規約に従い出典明示。外部媒体の紹介文は転載しない（theater spec 3. と同方針） |

## 6. 総括

Katsumascore が「レビューブログ」から「映画・アニメ総合メディア」へ拡張する上で、VOD配信情報は最良の入口である。理由は3つ。

1. **既にデータを持っている** — スクレイパーが8サービス分の配信状況を自動更新し続けており、追加の取得コストがない
2. **検索需要が大きく、かつ枯れない** — 「どこで見れる」「新着配信」は毎月・毎週更新され続けるクエリで、一度上位を取れば資産になる
3. **レビューへの導線が自然** — 「観れる場所」を知りたいユーザーは「観る価値があるか」も知りたい。配信情報とレビューは同一ユーザーの連続した関心である

一方で、ニュース化は諸刃の剣でもある。速報性で大手に勝つことはできず、量産に走れば独自性が薄まる。したがって本戦略の要は**役割分担の徹底**にある。

> ニュース・配信情報は入口に徹する。滞在と評価はレビューが担う。両者を内部リンクで強固に結ぶ。

そして着手順序として最も重要なのは、**新しいパイプラインを作る前に、既に持っているデータで取れる流入を取り切ること**である。構造化データ・「どこで見れる」最適化・サービス別ページのカレンダー化は、いずれも新規データ取得を必要とせず、既存の全記事に効く。Coming Soon パイプラインの未決定事項を解決するのはその後でよい。
