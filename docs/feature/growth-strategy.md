## 2. 戦略の骨格 — 「ニュースで集め、レビューで留める」

### 問題の構造

```
ニュース記事を増やす
  → 流入は増える
  → しかし「浅いサイト」と評価されるとレビューの権威性が毀損する
  → E-E-A-T 低下 → 全体の順位下落
```

Katsumascore の競争優位は**レビューの質と独自スコア**であり、速報性では映画.com・シネマトゥデイ・Filmarks に勝てない。したがって戦略は「ニュースで勝つ」ではなく役割分担にある。

### 3層モデル

```
┌─ 第1層：入口（Acquisition）────────────────────┐
│  週次まとめ記事（vod_publish） / 劇場公開 / Xニュース │
│  → 検索・Discover・SNSから「今」の需要を取る        │
│  KPI: セッション数、Discover表示回数、X経由流入       │
└──────────────────┬───────────────────────┘
                   │ 内部リンク（設計の要）
┌─ 第2層：回遊（Engagement）──────────────────┐
│  作品ページ / サービス別アーカイブ                  │
│  → 「何を観るか」の意思決定を支援                   │
│  KPI: セッションあたりPV、直帰率                    │
└──────────────────┬───────────────────────┘
                   │
┌─ 第3層：資産（Authority）───────────────────┐
│  レビュー / 考察 / person / company / series        │
│  → 独自スコアと文章。ここだけは代替不可              │
│  KPI: 滞在時間、指名検索、被リンク                  │
└──────────────────────────────────────────┘
```

第1層のページは単体で完結させず**必ず第2・第3層への導線を持つ**。逆に第3層のレビュー記事には**第1層の鮮度情報（今どこで観れるか）を埋め込む**。この双方向リンクが、ニュースの流入をレビューの評価に変換する機構になる。

> spec 11.2 の週次まとめ記事は既にこの原則に沿っている（作品カードに「レビューを読む」リンクを含む）。本書が追加するのは**逆方向**（レビュー記事 → 配信情報）の導線である。

## 3. フロント側のSEO是正【本書の中核】

`news_bot` パイプラインの外側にあり、既存ドキュメントが扱っていない領域。**新規データ取得が一切不要**で、既存の全記事に一括で効く。

### 3.1 `max-image-preview:large` の追加【優先度：S / 最優先】

リポジトリ内で `robots` メタタグが出力されているのは [`SeoHead.tsx:27`](../../../katsumascore-front/src/components/features/seo/SeoHead/SeoHead.tsx) の `noindex` 分岐のみで、**通常の記事ページには `robots` メタが一切出ていない**。`_document.tsx` にも記述はない。

この状態では Google は画像プレビューをデフォルトサイズ（小）に制限するため、**Google Discover に載る条件をそもそも満たしていない**。Discover は大きなカード画像が前提のフォーマットであり、事実上のブロッカーになっている。

対応は `_document.tsx` の `<Head>`（全ページ共通）に1行：

```tsx
<meta name='robots' content='max-image-preview:large, max-snippet:-1, max-video-preview:-1' />
```

> `SeoHead` の `noindex` 分岐と競合しないかは実機で出力HTMLを確認すること（`_document` と `next/head` はマージ経路が異なる）。

**本戦略で最も投資対効果が高い変更**。週次まとめ記事は鮮度・トピック性ともDiscover向きだが、この1行がない限り露出しない。

### 3.2 構造化データの是正【優先度：S】

[`SeoHead.tsx`](../../../katsumascore-front/src/components/features/seo/SeoHead/SeoHead.tsx) で `Product` + `Review` + `aggregateRating` + `BreadcrumbList` が既に出力されている。したがって本項は新規実装ではなく**是正**である。

**問題1：作品ページの `@type` が `Product`**（`SeoHead.tsx:54`）

映画・アニメ作品に `Product` を使っている。Google は映画に `Movie` / `TVSeries` を想定しており、`Product` では映画向けの拡張（監督・出演者・公開年のSERP表示）が効かない。`post.type` で分岐し、`director` / `actor` / `datePublished` / `genre` を付与すれば、既存の person・genre データがそのままSERPの情報量に変わる。

**問題2：`aggregateRating` の `reviewCount: 1`**（`SeoHead.tsx:76`）

`aggregateRating` は「複数評価の集約」を表すもので、評価1件なら `Review` 単体で表現するのが正しい。現状の形はレビュースニペットのガイドライン上無効と判定され★が表示されない可能性があり、自作自演レビューとみなされるリスクもある。

**推奨**：`aggregateRating` を外し `Review` + `reviewRating`（編集部による単一レビュー）に一本化。`author` はサイト名ではなく `Organization` または実名の `Person` にするとE-E-A-T上も整合する。

| スキーマ | 対象 | 状態 |
|---|---|---|
| `Movie` / `TVSeries` | 作品ページ | **要変更**（現状 `Product`） |
| `Review` + `reviewRating` | 作品ページ | 実装済み（`author` 見直し推奨） |
| `aggregateRating` | 作品ページ | **要削除または是正** |
| `BreadcrumbList` | 作品ページ | 実装済み |
| `ItemList` | 週次まとめ・一覧 | 未実装。4.3 とセットで追加 |

### 3.3 「どこで見れる」検索クエリの獲得【優先度：S】

映画・アニメの検索需要で最大級のクエリ群は「**{作品名} どこで見れる**」「**{作品名} 配信**」「**{作品名} netflix**」である。現在の勝者は JustWatch（日本語が機械翻訳的で薄い）と個人アフィリエイトブログ（情報が古くレビューがない）。

Katsumascore は**正確な配信情報（`vod_bot` が自動更新）＋独自レビュー＋スコア**を同時に持つ唯一のポジションにいる。

```
<title>『作品名』はどこで見れる？Netflix・U-NEXT配信状況とレビュー | Katsumascore</title>

H1: 作品名
H2: 『作品名』はどこで配信中？（← 配信状況テーブル）
H2: レビュー・評価（← 既存の本文）
```

**新規ページ不要**。既存の全レビュー記事のタイトル・見出し構造の調整だけで効く。VOD配信情報を持っているからこそ書ける見出しであり、「VOD情報がレビューへの入口になる」という本戦略の核心そのもの。

## 4. 既存データを活かす導線設計

`vod_bot` が既に持っているACFデータを、フロント側で使い切る施策。

### 4.1 レビュー記事 → 配信情報の逆方向導線【優先度：S】

improvements 6.（作品ページへの逆リンク）は spec 16. で「`vod_bot`側のACFフィールド追加が前提のため本施策単体では完結しない」と将来拡張に置かれている。

**しかし `vod_bot` 側のデータは既に揃っている。** `{service}_status` / `{service}_price` / `{service}_updated_at` はすべてACFに存在し、追加のフィールドは不要である。したがってこれは**フロント実装のみで完結する**。

```
▼ 配信中サービス
Netflix / U-NEXT（見放題）
Amazon Prime Video（レンタル ¥400）
最終確認: 2026-08-01
```

**「最終確認日」の明示が重要**。JustWatch・アフィリエイトブログに対する信頼性の差別化になると同時に、E-E-A-T の「情報の鮮度管理」シグナルにもなる。3.3 の見出し最適化とセットで実装する。

### 4.2 サービス別ページのカレンダー化【優先度：S】

improvements 3.（サービス別ページ連携）は spec 16. で将来拡張とされているが、**受け皿となる `/{locale}/vod/{service}` は既に実装済み**（`src/pages/vod/[slug]/index.tsx`）。ゼロからの新規構築ではなく**既存ページの強化**として扱える。

```
/ja/vod/netflix

【今週配信開始】   ← streaming_started_at が7日以内
【今月配信開始】   ← 30日以内
【Netflix 高評価レビュー】  ← review_score 降順
【配信中の全作品】  ← 既存のアーカイブ部分
```

- データは `streaming_started_at`（蓄積済み）を使うため**新規取得が不要**
- 「netflix 新作 映画」「アマプラ 新着」は検索ボリュームが大きく、かつ**毎月更新され続けるクエリ**（一度上位を取れば資産になる）
- 週次まとめ記事（`vod_publish`）からこのページへリンクすれば、第1層→第2層の導線になる

必要な作業：フロントの `/vod/[slug]` 拡張、WP REST API に `streaming_started_at` でのソート/絞り込み追加。

### 4.3 ジャンル×サービスの交差ページ【優先度：A】

improvements 5. の発展。単なるジャンル別ではなく**交差ページ**にすることでロングテールの獲得数が変わる。

```
/ja/vod/netflix/genre/sf     → 「Netflix SF映画 おすすめ」
/ja/vod/unext/genre/anime    → 「U-NEXT アニメ 見放題」
```

既存の genre taxonomy と vod taxonomy の AND 条件で自動生成できる。

> **必須の歯止め**：全組み合わせを機械的に生成すると薄いページが大量発生し逆効果になる。**作品数が10件以上ある組み合わせのみ生成**し、それ以下は生成しないか noindex にする閾値制御を必ず入れる。

### 4.4 年間/月間アーカイブ【優先度：B】

improvements 4. は優先度Aとされているが、**Bへの引き下げを提案する**。「2026年 Netflix追加作品」は「今週/今月」に比べ検索需要が明確に小さく、多くのユーザーは「今観れるもの」を探している。4.2 が効いてからその副産物として自動生成すれば足りる。

## 5. SNS施策

### 5.1 パイプラインのセットアップ完了【優先度：S / 前提条件】

VOD配信情報収集パイプラインは実装済みだが、**外部セットアップが未完のため動いていない**（spec 14./15.）。

- GitHub Secrets 登録（`VOD_NEWS_WP_*`）
- WordPress側のCPT登録（`register_post_type`）+ Application Password 発行
- 「VOD情報源」シートへのX公式アカウント6件の登録（ハンドルの実在確認が必要、spec 15.#7）

**第1層の入口コンテンツはここが動かないと生まれない。** 本戦略のSNS施策・Discover施策はすべてこの完了が前提になる。

### 5.2 プラットフォーム分散【優先度：A】

X 単独依存はリーチ上限・API費用の両面でリスクがある。spec 16. に「Threads / Bluesky向け文面生成」として既に挙げられており、`compose_vod.py` の出力を流用できる。

| プラットフォーム | コスト | 特性 |
|---|---|---|
| **Threads** | API無料 | 日本の映画・アニメ層が厚い。文面をほぼそのまま流用可 |
| **Bluesky** | API無料 | 競合が少なく相対的に目立つ |
| **Instagram** | API無料 | ビジュアル資産があれば強い。ポスター著作権に注意 |

**Threads と Bluesky は同一投稿文を流用でき追加コストがほぼゼロ**。X API の従量課金を増やさずリーチを広げられるため、優先度が高い。

## 7. 測定設計

| 指標 | 取得元 | 目的 |
|---|---|---|
| ページ種別ごとのセッション | GA4（カスタムディメンション） | 3層の流入内訳 |
| **第1層 → 第3層の遷移率** | GA4 経路探索 | **本戦略の成否を測る最重要指標** |
| Discover 表示回数・CTR | Search Console | 3.1 の効果測定 |
| 「どこで見れる」系クエリの順位 | Search Console | 3.3 の効果測定 |

**第1層→第3層の遷移率が低いままセッションだけ増えている場合**、ニュースが浅いトラフィックを呼んでいるだけで戦略が機能していない。この場合は施策を増やさず内部リンク設計を見直す。

## 8. リスクと歯止め

| リスク | 内容 | 歯止め |
|---|---|---|
| **薄いページの量産** | 交差ページ・アーカイブの自動生成で低品質ページが増える | 作品数10件未満は生成しない閾値制御（4.3・4.4 に必須適用） |
| **AI発見の誤情報** | ハルシネーション・日付誤りをそのまま公開 | spec の人間承認フローを維持。CPTは `draft` 投稿のまま運用（spec 11.2）。精度検証を数週実施（spec 15.#6・#10） |
| **レビューの希薄化** | ニュース記事比率が上がり「レビューサイト」の認知が薄れる | 第3層の更新頻度を維持。TOP・サイト構造ではレビューを主役に置く |
| **配信情報の誤り** | スクレイパー誤判定で誤情報を掲載 | 「最終確認日」の明示（4.1）。`ended` 判定は保守的に |
| **規約違反** | 新情報源の追加時に規約を確認せず取り込む | シート登録前に人間がブラウザで規約原文を確認（spec 17.）。[vod-sources-candidates.md](./vod-sources-candidates.md) の判断基準を適用 |
| **X API コスト** | 自動投稿再開時に従量課金が膨らむ | 手動投稿方式を維持。無料APIのThreads/Blueskyを先に拡張 |
| **著作権** | あらすじ・紹介文の転載 | 事実情報のみ保存・掲載（spec 3.非ゴール・17.と同方針） |

## 9. 総括

VOD配信情報が入口として最良である理由は3つ。

1. **既にデータを持っている** — `vod_bot` が8サービス分の配信状況を自動更新し、`news_bot` の収集パイプラインも実装済み
2. **検索需要が大きく枯れない** — 「どこで見れる」「新着配信」は毎週・毎月更新され続けるクエリで、一度上位を取れば資産になる
3. **レビューへの導線が自然** — 「観れる場所」を知りたいユーザーは「観る価値があるか」も知りたい

一方で、速報性で大手に勝つことはできず、量産に走れば独自性が薄まる。したがって要は役割分担にある。

> ニュース・配信情報は入口に徹する。滞在と評価はレビューが担う。両者を内部リンクで強固に結ぶ。

**現時点で最も効率が良いのは Phase 1 のフロントSEO是正**である。`max-image-preview:large` の1行と JSON-LD の型是正は、パイプラインの稼働を待たず、既存の全記事に即座に効く。特に前者は、せっかく週次まとめ記事を作ってもDiscoverに露出しない状態を解消するものであり、パイプラインを立ち上げる前に済ませておくべき前提整備にあたる。
