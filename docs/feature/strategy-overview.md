# Katsumascore 戦略・役割分担・運用方針

作成日: 2026-08-03
位置付け: 配信情報を軸とした流入拡大施策の**全体像**。個別の実装仕様は各仕様書に委ねる。

---

## 1. 目指す姿

Obsidian Vault の [SEO Strategy](../../obsidian/SEO/SEO.md) が掲げる方向と同じ。

> Katsumascoreはレビューサイトではなく、映画・アニメ・ドラマ・VODの**総合検索メディア**を目指す。

本書はその中で **「配信情報（VOD・劇場）を入口にした流入拡大」** の部分を担当し、
既存のSEO戦略（Person / Series / Genre / Year / Collection の縦展開）と補完関係に立つ。

| 既存のSEO戦略 | 本戦略 |
|---|---|
| **静的な軸**でページを増やす（人物・シリーズ・ジャンル・年代） | **時間軸**で鮮度を作る（今週配信・今週公開） |
| 検索の網羅性を上げる | Discover・SNS・「今」の検索需要を取る |
| ロングテールの資産形成 | 定期的な更新シグナルと入口の供給 |

両者は競合せず、**同じ作品ページ（Movie）に対して別方向から導線を作る**関係にある。

## 2. 戦略の骨格 — 「ニュースで集め、レビューで留める」

### なぜ役割分担が必要か

速報性では映画.com・シネマトゥデイ・Filmarks に勝てない。一方でニュースを量産すれば
「浅いサイト」と評価され、Katsumascore の競争優位である**レビューの質と独自スコア**まで
毀損しかねない（E-E-A-T低下 → サイト全体の順位下落）。

したがって「ニュースで勝つ」のではなく、層ごとに役割を分ける。

### 3層モデル

```
┌─ 第1層：入口（Acquisition）────────────────────┐
│  週次まとめ記事 / 劇場公開カレンダー / Xニュース      │
│  役割: 「今」の需要を取る。鮮度とDiscover            │
│  KPI: セッション数、Discover表示回数、SNS経由流入      │
└──────────────────┬───────────────────────┘
                   │ 内部リンク（設計の要）
┌─ 第2層：回遊（Engagement）──────────────────┐
│  作品ページ / サービス別アーカイブ / ジャンル交差      │
│  役割: 「何を観るか」の意思決定を支援                │
│  KPI: セッションあたりPV、直帰率                    │
└──────────────────┬───────────────────────┘
                   │
┌─ 第3層：資産（Authority）───────────────────┐
│  レビュー / 考察 / Person / Series / Collection      │
│  役割: 独自スコアと文章。ここだけは代替不可           │
│  KPI: 滞在時間、指名検索、被リンク                  │
└──────────────────────────────────────────┘
```

**設計原則**

- 第1層のページは単体で完結させず、**必ず第2・第3層への導線を持つ**
- 第3層のレビュー記事には、**第1層の鮮度情報（今どこで観れるか）を埋め込む**
- この双方向リンクが、ニュースの流入をレビューの評価に変換する機構になる

## 3. 役割分担

### 3.1 パイプラインの責務（最も混同しやすい点）

VOD関連で3つのパイプラインが並走している。**それぞれ責務が異なる**。

| | `vod_bot`（weekly_patch） | `news_bot`（vod_discover / vod_publish） | `news_bot`（theater） |
|---|---|---|---|
| **責務** | **既存WP投稿**の配信状況を更新 | **新規に配信開始する作品**の発見・発信 | 劇場公開作品の発見・発信 |
| **手段** | 各サービスURLへのチェッカー巡回 | X API + AI Web検索 | AI Web検索 |
| **出力** | ACF更新・vod taxonomy同期 | Sheets → 週次まとめCPT記事 | Sheets → Slack投稿案 |
| **人間の関与** | なし（全自動） | **承認必須** | **承認必須** |
| **本戦略での役割** | 第2層のデータ源 | 第1層のコンテンツ生成 | 第1層のコンテンツ生成 |

> **要点**: `vod_bot` は「すでに記事がある作品の配信状況」、`news_bot` は「まだ記事がないかもしれない新規配信作品」を扱う。前者はフロント表示（4.1・4.2）に、後者は週次まとめ記事に使う。

### 3.2 リポジトリの責務

| リポジトリ | 本戦略での担当 |
|---|---|
| `vod_scraping_api` | 配信状況の取得（`vod_bot`）・配信情報の収集と記事生成（`news_bot`）・**本戦略ドキュメント** |
| `katsumascore-front` | **SEO是正（構造化データ・robotsメタ）**・配信状況の表示・サービス別ページ・内部リンク |
| `katsumascore_wordpress_theme` | CPT登録（`vod_release`）・ACFフィールド・REST API拡張（`streaming_started_at` ソート等） |

**Phase 1 の施策はすべて `katsumascore-front` 側**にある点に注意。本リポジトリの作業ではない。

### 3.3 ドキュメントの責務

| ドキュメント | 扱う範囲 |
|---|---|
| [vod-release-calendar-spec.md](./vod-release-calendar-spec.md) | 配信情報の収集〜週次まとめ記事生成（`news_bot/`）。**実装済み** |
| [vod-release-calendar-improvements.md](./vod-release-calendar-improvements.md) | 上記へのブランド価値向上10案 + 反映状況の対応表 |
| [vod-sources-candidates.md](./vod-sources-candidates.md) | 情報源の規約調査・コスト試算 |
| [theater-release-calendar-spec.md](./theater-release-calendar-spec.md) | 劇場公開カレンダー（方式の親） |
| [growth-strategy.md](./growth-strategy.md) | フロント側SEO是正 + サイト全体の導線設計 |
| **本書** | 全体像・役割分担・運用方針 |

**原則**: パイプライン内部の仕様変更は spec 側、フロント側の実装は growth-strategy 側で扱い、
本書は両者をまたぐ判断のみを記載する。

### 3.4 人間とAIの役割分担

既存の [SEO Strategy](../../obsidian/SEO/SEO.md) の AI Policy を踏襲する。

| 担当 | 範囲 |
|---|---|
| **AI** | 配信情報の発見・構造化抽出・紹介文/見出しの生成・関連記事の提示 |
| **人間（必須）** | **配信情報の承認**・編集部おすすめの選定とコメント・**レビューの最終編集**・SNSへの実投稿・新規情報源の規約確認 |

AI発見は誤り得る（ハルシネーション・日付誤り）ため、**承認を経ずに公開へ流さない**のが
全パイプライン共通の原則。CPT投稿も当面は `draft` 固定とする。

## 4. 制約（動かせない前提）

2026-07-22 に人間が規約原文を確認済み。詳細は [vod-sources-candidates.md](./vod-sources-candidates.md)。

| 手段 | 判断 |
|---|---|
| 各VODサービス公式サイトのスクレイピング | **不採用確定**（対象6サービスすべてが自動化アクセスを規約で明示禁止） |
| TMDb スクレイピング | 不採用 |
| TMDb API | 商用契約（$149/月〜）成立時のみ将来採用 |
| VODサービス公式Xアカウント（X API v2） | **採用**。サービス別一次情報の唯一の機械取得ルート |
| AI Web検索（Claude / OpenAI） | 採用（既定） |

Katsumascore は AdSense で収益化しているため、**「商用利用禁止」「自動化アクセス禁止」の
両方に抵触しないこと**が情報源の採用条件になる。

> **方針**: 新たな外部データ取得を必要とする施策は提案しない。既に持っているデータ
> （`vod_bot` のACF + `news_bot` の収集結果）だけで実現できる施策に限定する。
> 新情報源を追加する場合は、シート登録前に**人間がブラウザで規約原文を確認する**。

## 5. 現状と着手順序

### 5.1 現状サマリ

| 領域 | 状態 |
|---|---|
| VOD配信状況スクレイピング（`vod_bot`） | ✅ 稼働中 |
| VOD配信情報収集パイプライン（`news_bot`） | ⚠️ **実装済み・外部セットアップ未完で未稼働** |
| 劇場公開カレンダー | ✅ 実装済み（承認待ち保存まで） |
| news_bot（RSS / 公式X） | ⏸ 稼働中だが cron 一時停止中 |
| `/{locale}/vod/{service}` アーカイブ | ✅ 実装済み（強化余地あり） |
| フロント構造化データ | ⚠️ **実装済みだが要是正** |
| `max-image-preview:large` | ❌ **未設定（Discoverのブロッカー）** |

### 5.2 着手順序の原則

> **新しいデータ取得を作る前に、既にあるデータで取れる流入を取り切る。**

理由は3つ。

1. Phase 1 の施策は**新規データ取得もページ追加も不要**で、既存の全記事に一括で効く
2. `max-image-preview:large` が未設定のままでは、週次まとめ記事を作っても**Discoverに露出しない**。パイプラインを立ち上げる前に済ませるべき前提整備にあたる
3. 構造化データの是正は、順位を変えずにCTRを改善しうる

### 5.3 ロードマップ

**Phase 1 — フロントSEOの是正**（`katsumascore-front` / パイプライン非依存）

| # | 施策 | 工数感 |
|---|---|---|
| 1 | `max-image-preview:large` を `_document.tsx` に追加 | **1行** |
| 2 | JSON-LD 是正（`Product`→`Movie`/`TVSeries`、`aggregateRating` 見直し） | 小 |
| 3 | 「どこで見れる」タイトル・見出し最適化 | 小〜中 |
| 4 | 作品ページの配信状況ブロック（`vod_bot` のACFを表示） | 中 |

**Phase 2 — パイプライン稼働と導線接続**

| # | 施策 | 担当 |
|---|---|---|
| 5 | 外部セットアップ（Secrets / CPT登録 / Application Password / Xアカウント登録） | WP・運用 |
| 6 | AI発見の精度検証（数週運用） | 運用 |
| 7 | サービス別ページのカレンダー化 | front + WP API |
| 8 | 週次まとめ記事 ⇔ サービス別ページの相互リンク | front + news_bot |
| 9 | Threads / Bluesky 展開 | news_bot |

**Phase 3 — ロングテール拡張**

交差ページ（閾値制御付き）・年間アーカイブ・承認フローのワンクリック化・SNS優先度のAI判定。

## 6. 運用方針

### 6.1 コンテンツ

- 外部サイトの本文・あらすじ・紹介文は**転載しない**（事実情報のみ）
- 週次まとめ記事は配信情報の羅列で終わらせず、**レビュー記事への内部リンクを必ず入れる**
- 編集部おすすめは**人間が選定**する。自動生成一覧との差別化要素であり、Helpful Content 評価上も重要
- レビューは**必ず人が最終編集**する（既存 AI Policy を踏襲）

### 6.2 品質の歯止め

| リスク | 歯止め |
|---|---|
| 薄いページの量産 | 交差ページ・アーカイブは**作品数10件以上の組み合わせのみ生成**。それ未満は生成しないか noindex |
| AI発見の誤情報 | 人間承認フローを維持。CPTは `draft` 投稿。精度検証を数週実施 |
| 配信情報の誤り | **「最終確認日」を明示**。`ended` 判定は保守的に |
| レビューの希薄化 | 第3層の更新頻度を維持。TOP・サイト構造ではレビューを主役に置く |
| 規約違反 | 新情報源はシート登録前に人間が規約原文を確認 |
| X API コスト | 手動投稿を維持。無料APIの Threads / Bluesky を先に拡張 |

### 6.3 測定

| 指標 | 取得元 | 用途 |
|---|---|---|
| **第1層 → 第3層の遷移率** | GA4 経路探索 | **本戦略の成否を測る最重要指標** |
| ページ種別ごとのセッション | GA4 カスタムディメンション | 3層の流入内訳 |
| Discover 表示回数・CTR | Search Console | Phase 1-1 の効果 |
| 「どこで見れる」系クエリ順位 | Search Console | Phase 1-3 の効果 |
| リッチリザルト表示 | Search Console 拡張レポート | Phase 1-2 の効果 |
| SNS経由セッション | GA4（UTM） | Phase 2-9 の効果 |

**判断基準**: 第1層→第3層の遷移率が低いままセッションだけ増えている場合、ニュースが
浅いトラフィックを呼んでいるだけで戦略が機能していない。この場合は**施策を増やさず
内部リンク設計を見直す**。

## 7. まとめ

配信情報が入口として最良である理由は3つ。

1. **既にデータを持っている** — `vod_bot` が9サービスの配信状況を自動更新し、`news_bot` の収集パイプラインも実装済み
2. **検索需要が大きく枯れない** — 「どこで見れる」「新着配信」は毎週・毎月更新され続けるクエリで、一度上位を取れば資産になる
3. **レビューへの導線が自然** — 「観れる場所」を知りたいユーザーは「観る価値があるか」も知りたい

一方で、速報性で大手に勝つことはできず、量産に走れば独自性が薄まる。要は役割分担にある。

> **ニュース・配信情報は入口に徹する。滞在と評価はレビューが担う。両者を内部リンクで強固に結ぶ。**

そして着手順序として最も重要なのは、**新しいパイプラインを立ち上げる前に、
既に持っているデータで取れる流入を取り切ること**である。
